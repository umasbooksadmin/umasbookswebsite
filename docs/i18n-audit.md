# French audit

Decision (maintainer, 2026-10-02): everything customers see is French when they select French. Pages, messages after a form, emails and the text built by scripts in the browser. The **admin area stays English**, except anything an admin action sends to a customer (emails, notices).

This file says where we stand, how it is checked, what is deliberately not translated, and how to add a new text so it stays translated. Keep it up to date: `node scripts/i18n-audit.js --write` refreshes the table below.

## How the audit works

Everything below runs in CI as part of `npm test`.

1. **Crawler** (`test/integration/i18nCrawler.test.js`, helper `test/helpers/i18nCrawl.js`). Starts the real app on its own database, seeds one of everything a customer can see (books with awards and several conditions, events, sessions, a meeting, shifts, a forum thread, a charity round, an announcement, orders), then
   * reads every customer page as a **guest, an account holder, a member and a volunteer**, in English and in French (cookie `umasbooks_lang`);
   * runs 59 **form scenarios** (wrong password, empty fields, signup, forgot password, contact, book request, cart and reservation, event sign-up, privacy export and delete, two-step, forum, charity vote, meetings, CSRF refusal, a customer at an admin address...) and reads the page, JSON or text the person is left on;
   * reads the **JSON APIs** (search, new in, events, cart count, session);
   * reads every **email** the app sends during those scenarios (captured at the mailer, so one-time-link mails are seen with their full text).
   It extracts the visible text and the text-bearing attributes (`title`, meta description, Open Graph, `alt`, `aria-label`, `placeholder`) and flags French text that is **identical to the English page**, **equal to a known English `tr()` string**, or **contains English function words** (the, your, please, click...). A brand lockup ("Uma's Books and Adventures") is not scored. It also checks that every French page says `<html lang="fr">`.
2. **Pairs test** (`test/unit/frenchWording.test.js`): every `tr(english, french)` call in views, routes and libs (about 640), and every marketing page dictionary: French present, not a copy of the English, no English function words, "e-mail" with a hyphen, the same `{placeholders}`; EN and FR dictionaries have the same keys.
3. **Source scan** (`test/unit/frenchSourceScan.test.js`): customer-facing server code (non-admin routes, middleware, the libraries that build customer messages) must not gain an English sentence outside `tr()`. What it finds today was read once: SQL fragments, log lines, messages for the admins, the English half of an `{en, fr}` pair, data sent to the admins. It is listed in `test/i18n-source-baseline.json`.
4. **Typography** (`test/unit/frenchTypography.test.js`, `pageDictionary.test.js`): no-break space before `; : ! ? »` and `€`, curly apostrophes, on pages and in French emails.
5. **English did not change**: `node scripts/i18n-audit.js --dump-en` writes the English text of every crawled page; diff the file from `main` against your branch (done for the audit PRs: identical).

Run it yourself (needs a local Postgres):

```bash
cd umas-books
node scripts/i18n-audit.js            # prints pages with English left; ends with TOTAL flagged: 0
node scripts/i18n-audit.js --dump     # every French text with its page: /tmp/i18n-fr-dump.txt
npm test                              # includes the crawler (about half a minute)
```

## Definition of done: adding a customer-facing text

A text is done when a French reader sees French. Checklist:

1. **A view or route** (`views/*.ejs`, `src/routes/*.js`): write `tr('English', 'Français')` in a view, `req.tr('English', 'Français')` in a route. Placeholders: `tr('Hello {name}', 'Bonjour {name}', { name })`. Counts: French 0 and 1 are singular, so `tr('{n} votes', n < 2 ? '{n} vote' : '{n} votes', { n })`.
2. **A marketing page**: the text gets a `data-i18n="key"` and the key goes in **both** `pageI18nEn` and `pageI18nFr` of the page (or in `COMMON` in `assets/site.js` when shared). A new page needs `meta.title` and `meta.description` in both.
3. **An email**: `const tr = emailTr(lang)` and `tr('English', 'Français')`; the language comes from `users.lang`, `orders.lang` or `book_requests.lang`.
4. **A script in the browser** (`public/*.js`, `assets/*.js`): take the text from the page's dictionary or read `<html lang>`; never hard-code an English string.
5. **A message from a JSON API**: use `req.tr` / `req.lang`.
6. **Attributes count**: `title`, `alt`, `aria-label`, `placeholder`, `<option>` labels, button `value`s, the meta description.
7. **Typography**: write the French with plain spaces and straight apostrophes in `tr()` strings; the page and email filters add the no-break spaces and curly apostrophes. In dictionaries write ` ` before `: ; ! ? €` yourself (a test checks).
8. **Vocabulary**: vous; réservation, adhésion / adhérent(e), bénévole, librairie, livre d'occasion, état (Neuf, Comme neuf, Très bon état, Bon état, État correct), reliure (Poche, Broché (grand format), Relié), panier, retrait en boutique, régler sur place, mot de passe, e-mail, Se connecter / Se déconnecter / Créer un compte, Espace membres. Prices through `formatEuro` / `eur()`, dates through the `formatDate*` helpers.
9. **Run** `npm test` (the crawler, the pairs test and the source scan name the file and the text if you missed one) and `npm run lint`.
10. **If the same text really is the same in both languages** (a brand, a legal identifier, a word spelled alike): add it to `test/i18n-allowlist.js` **with a reason**. Never to hide a missed translation.
11. **Not for customers** (admin screens, mails to the admins, logs): leave in English. If the source scan complains about a new such literal, add it to `test/i18n-source-baseline.json`.

## Not translated on purpose

The allow-list (`test/i18n-allowlist.js`), with reasons:

| Text | Reason |
|------|--------|
| Uma's Books and Adventures (all spellings), "and Adventures" on the dashboard | the brand name, kept exactly |
| UMAS BOOKS, RNA, SIRET, SIREN, Hippolyte Savary, Rue Peyrolière, Albi | legal entity, identifiers and addresses |
| HelloAsso, Instagram, Facebook, Google, Render, Cloudflare, Backblaze, GitHub, Anthropic, CM2C | company and service names in the privacy policy and legal notice |
| Little Explorers, Éveil English, Young Adventurers, Young Readers, Teen Literature, English Café, Éveil | program names, English (or French) on purpose |
| `umasbooks_lang` | the literal name of the language cookie in the legal notice |
| Message, Code | spelled the same in French |
| `1 vote` | spelled the same in French |
| the generated two-step key (32 letters/digits) | a secret to type into an app |
| TVA non applicable..., the consumer-law notice (art. D211-2) | French legal text, required as written, in both languages |
| `Crawl ...` | the crawler's own seeded data |

Not on the list because the crawler never sees it, but also not translated:

* **Stored content** written in one language: book titles, authors, publishers, **award names** (from Wikidata and the NYT, as stored), blog posts, announcements, forum posts, event and session titles and descriptions, meeting agendas and minutes, volunteer shift notes, charity names and descriptions. Books have a French description column (`description_fr`) and genres a French label; the others do not. See "Questions" below for the blog.
* **The admin area**, the emails the site sends to the admins (contact form, forum reports, digests, alerts) and the till.
* **Field names** in the downloadable JSON data file (the database's names); its explanatory note follows the language.
* `robots.txt`, `sitemap.xml`, the `.ics` calendar file (event data).
* The HelloAsso payment form (their page, their language).

Legal texts (terms of sale, legal notice, privacy policy, membership terms) are French first, and each also has an English version selected by the EN toggle. Nothing in them was rewritten.

## Questions for the maintainer

Things I was not sure about; nothing was changed for them unless said.

1. **"e-mail" or "courriel"**. The legal pages and almost all French text already say "e-mail" (112 times, "courriel" never), so I kept it and fixed the three "email" slips. A test now requires the hyphen.
2. **French-only legal block in the French reservation e-mail** (changed). It used to repeat the whole block in English as well, on purpose ("never reduced to one language"). A French reader now gets French only; the English e-mail still has both. If a lawyer wants both languages in both mails, revert `buildOrderConfirmationText` in `src/lib/orderEmail.js` (one line) and `test/unit/orderConfirmationEmail.test.js`.
3. **"drop-in"** is kept inside French text (« drop-in », as the terms of sale write it) next to "à la carte" on the marketing pages. Choose one: « séance à l'unité » reads more naturally for a small shop. It appears in the terms of sale, privacy policy, cart, account and emails.
4. **The membership page shows the expiry date as `2027-04-27`** in both languages. This was done on purpose (an ISO date reads the same in both languages and does not go stale when the toggle is pressed). A French "27 avril 2027" would need the date to be swapped by the toggle script too. Say if you want it.
5. **Blog posts, announcements, event and session descriptions, forum posts have no French field.** The three starter blog posts (imported in migration 027) are English only, so a French visitor sees English posts on the home slider and on the blog page. Options: add `title_fr / body_fr` columns and admin fields (a schema and admin change, so not done here), or write posts in both languages in one text. The crawler leaves the blog JSON out for that reason.
6. **Two French wordings for the same generic error**: "Une erreur s'est produite. Veuillez réessayer." (error pages) and "Une erreur est survenue. Veuillez réessayer." (login pages). Both are fine; pick one if you like.
7. **Tone**: the French uses "Veuillez ..." (formal) in errors and plain "vous" sentences elsewhere. One place is warmer than the rest: "Désolé, votre message n'a pas pu être envoyé" (contact); "Nous sommes désolés" would match the others.
8. **Apostrophes and quotes in e-mails** are mixed: some mails use the curly ’ and others a straight '. I added the no-break spaces but did not touch apostrophes in mails, because names typed by people (O'Brien) pass through the same text.
9. **"Espace membres"** (the members' area in French) is used everywhere; the page title says "Uma's Books — Espace membres". The English side calls it "Members Area".
10. **A customer who opens an admin address** now gets "Réservé aux administrateurs." in French (English: "Admins only."). The page itself is plain text.
11. **Event with price 0** shows "0,00 €" in the calendar (English "€0.00") next to "Paiement sur place"; a free event with no price shows "Gratuit". Not a translation issue, but you may want "Gratuit" for 0 too.

## What the crawler does not cover

* Text built by JavaScript in the browser after the page loads (the books search results, the favourites list, the calendar on the events page, the home slider): the dictionaries are checked for matching keys and for French content (`frenchWording`), and `pageDictionary` tests the swap, but the rendered result is checked by `node scripts/i18n-audit-browser.js` (a real headless Chrome loads those pages in both languages and presses the FR toggle; not part of `npm test` because it needs Chrome), by the browser tests (`npm run e2e`) and by `docs/testing/french-review.md`. Last run: nothing left in English except the stored blog posts (question 5) and the genre words "Fiction" and "Romance", which are French words too.
* States that need an outside service (a HelloAsso payment, the real SMTP server, the till).
* The mails that need a long wait (the day-10 pickup reminder, the seat reminder, "reservation ended", the inactive-account warning, the forum statement of reasons, the "we found your book" mail): their texts are `tr()` pairs and are covered by the pairs test and by the integration tests that build them in French (`reservationSweeps`, `forumModeration`, `i18nShop`, `orderConfirmationEmail`).

## Inventory (what the audit covers)

* **Views**: `views/*.ejs` (36 customer pages: account, privacy, 2FA, auth, cart, book, forum, meetings, volunteer, requests, errors...), `views/partials/` (header, footer, calendar items, banners, privacy note), `views/marketing/*.ejs` (14 pages + home, each with an EN and an FR dictionary). `views/admin/` is out of scope.
* **Dictionaries**: `pageI18nEn/Fr` in each marketing view, `COMMON` in `assets/site.js`, `memNewEn/Fr` on the membership page.
* **Server messages**: `req.tr(...)` in `src/routes/*.js`, `src/middleware/*.js`, `src/lib/errorHandler.js`.
* **Emails**: `src/lib/orderEmail.js` (reservation, reminder, ended, seat reminder), `emailVerification.js`, `passwordReset.js`, `bookRequests.js`, `privacy.js`, `reservations.js`, `forumModeration.js`, `src/routes/accountPrivacy.js`, `src/lib/orderSweeps.js`.
* **JSON APIs**: `/api/books/*`, `/api/events/upcoming`, `/api/cart/count`, `/api/session`, `/api/favorites/toggle`, `/api/csrf-token`.
